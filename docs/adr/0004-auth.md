# ADR 0004: Better Auth on Forge's identity tables

| | |
|---|---|
| **Status** | Accepted for V1. Proven locally through PgBouncer in transaction mode. **Implemented in M2-1** (see the addendum) |
| **Date** | 2026-09-30 |
| **Spike** | S4 / M0-6 (v1-github-issues.md) |
| **Decisions touched** | D-07 (clarified, not changed), D-06 |

## Question

Can Better Auth run on Forge's own tables (`users`, `auth_accounts`, `auth_sessions`, `auth_verifications`), with UUIDv7 ids and DB sessions (`cookieCache` off)? Can it do this without its own data model, and without touching tenancy, RBAC or membership? And can it deliver the V1 configuration in v1-build-plan §12?

## Setup

- `better-auth` **1.7.6**, pinned exactly (`--save-exact`); `better-auth/adapters/drizzle` with `provider: "pg"`.
- The adapter gets Better Auth's model names mapped to our tables: `{ user: users, account: authAccounts, session: authSessions, verification: authVerifications }`. No renaming config is needed, because the Drizzle property names already match Better Auth's field names. Columns stay snake_case.
- `advanced.database.generateId: () => uuidv7()`.
- The adapter uses the pooled `forge_app` connection (the same shape as production), through `identityDb()` (see discovery 1).
- Spike code: `spikes/auth/auth.ts` (config) and `spikes/auth/auth.integration.test.ts` (removed in M2-1; the configuration is now `src/modules/auth/auth.ts` and the tests are `tests/integration/auth.test.ts`). Every test goes through `auth.handler(Request)`, the same entry point `/api/auth/[...all]` uses.

## Evidence

`npm run test:integration` runs **16 spike tests, all passing** (2026-09-30, local):

| Requirement | Test |
|---|---|
| Sign-up writes our tables; all ids are UUIDv7; email lowercased | `sign-up` → `writes to users / auth_accounts / auth_sessions…` |
| Password hashing: salted scrypt only, never plaintext | `stores the password only as a salted scrypt hash` |
| Minimum 12 characters | `rejects passwords shorter than 12 characters` |
| Cookie: host-only, HttpOnly, `SameSite=Lax`, 7-day Max-Age; `Secure` + `__Secure-` on https | two cookie tests |
| Identity only: sign-up creates no organization or membership | `creates identity only…` (read in the user's own RLS context) |
| Verification flow: link sent on sign-up, following it sets `email_verified`; a tampered token is rejected | `email verification` |
| Login (case-insensitive email) + session retrieval from the cookie | `logs in with the right password…` |
| Generic error: wrong password ≡ unknown email (same status, same body) | `gives the same generic error…` |
| Logout deletes the session row and clears the cookie | `logout deletes the session row…` |
| Revocation takes effect on the very next request; other sessions survive | `a revoked session fails on the very next request…` |
| 7-day sliding idle window, 30-day absolute cap | `slides the idle window, but never past created_at + 30 days` (fails if the cap hook is removed; checked) and `a fresh session slides by the full 7 days` |
| Google OAuth ready: authorization-code + PKCE (S256), our callback URL, state stored in `auth_verifications` (UUIDv7); unknown state rejected | `Google OAuth readiness` |

## Decision

Use Better Auth as designed (D-07) with the configuration in `spikes/auth/auth.ts`. M2-1 moves it into `src/modules/auth`. No fallback is needed: UUIDv7 works natively, so the "UUIDv7 or documented fallback" criterion takes the first branch.

## Discoveries (clarifications to the plan; no scope change)

1. **The adapter needs a database handle, not a transaction callback.** Better Auth issues its own queries, so it can't run inside `withTenant()`. `src/platform/db/identity.ts` exports `identityDb()` for this. ESLint only lets `modules/auth` import it (with a unit test), and the raw client stays private to `platform/`. This is safe by construction: the identity tables have no RLS (class `identity`), and the handle carries no tenant context, so every tenant table reads as empty through it.
2. **Better Auth has no absolute session lifetime.** It only slides `expires_at` by `expiresIn` when `updateAge` has passed. The 30-day cap from §12 is a `databaseHooks.session.update.before` hook that clamps the new `expires_at` to `created_at + 30 days`. The hook reads the session from `ctx.context.session`, which `getSession` sets before it refreshes. That is library behaviour, not a documented contract, so the version stays pinned and the test fails if an upgrade breaks it.
3. **OAuth linking already matches §12.** `account.accountLinking.requireLocalEmailVerified` defaults to `true` (the flag is deprecated because it's becoming unconditional). Google is linked to an existing user only when Google asserts `email_verified` *and* the local user has verified the same address. That blocks pre-registration takeover. We set no `trustedProviders`.
4. **Hashing is scrypt through `node:crypto`**: N=16384, r=16, p=1, 16-byte salt, 64-byte key, stored as `salt:key` hex. It runs on the libuv thread pool, so it doesn't block the event loop.
5. **Emails are lowercased by Better Auth** on sign-up, sign-in and update. That agrees with the `users_email_lowercase` CHECK constraint.
6. **Email-verification tokens are signed JWTs, not rows.** They expire after 1 hour by default, and following one twice is harmless. OAuth state (and, in M2-3, password-reset tokens) *are* rows in `auth_verifications`.
7. **Telemetry is off by default.** The config sets `telemetry: { enabled: false }` explicitly anyway, so a future default change can't turn it on.
8. **For M2-4: the built-in rate limiter stores counts in memory by default.** On Vercel that is per instance, so it is best-effort only. The Vercel WAF rule on `/api/auth/*` (already in M2-4) is the real limit. Better Auth also supports `rateLimit.storage: "database"`, but that needs a table that isn't in the V1 schema. Add it only if the WAF rule proves insufficient.
9. **For M2-1: `getCurrentUser()` reads request headers**, which makes the component that calls it dynamic under Cache Components. Admin layouts must call it inside a Suspense boundary (or in a dynamic segment). Check this when M2-1 wires the helpers into `(admin)`.

## Not covered by this spike (owned by later issues)

- Email delivery through `email.send` jobs: M1-4 / M2-1. The spike captures the verification link in a callback.
- Password reset and the full Google callback with a real Google account: M2-3. The reset options (`resetPasswordTokenExpiresIn`, `revokeSessionsOnPasswordReset`) exist in 1.7.6.
- Rate limits, Turnstile and the audit rows: M2-4.

## Addendum (M2-1, 2026-10-03): the production implementation

No decision above changes. This records how the spike became `src/modules/auth`, and what the implementation had to clarify.

### Layout

```text
/api/auth/[...all]  →  authRouteHandlers  →  Better Auth  →  identityDb() (users, auth_*)
                                                 └→ sendEmailSoon() → email.send job → EmailProvider   (ADR 0007)

application code    →  getCurrentAuth() / requireUser() / requireVerifiedUser()   (modules/auth)
                         └→ { user, session } in Forge's own types; null when anonymous
```

| File | Role |
|---|---|
| `auth.ts` | The only Better Auth configuration (`createAuth`), built lazily on first use |
| `config.ts` | Reads the `auth` env group; resolves the base URL and the secret |
| `session.ts` | Forge's session abstraction and guards |
| `errors.ts` | Better Auth error → `AppError` |
| `log.ts` | Better Auth log lines → Forge's JSON logger |
| `shared.ts` | Types and constants that are safe to import anywhere (`AuthUser`, `Actor`, `MIN_PASSWORD_LENGTH`) |

ESLint still allows Better Auth imports only inside `modules/auth`.

### Clarifications

1. **Forge's session shape.** `resolveAuth(headers)` returns `{ user: { id, email, name, emailVerified, image }, session: { id, createdAt, expiresAt } }` or `null`. Better Auth's token, IP address and user agent never cross that line. `toActor()` gives `{ kind: "user", userId, sessionId, emailVerified }` or `{ kind: "anonymous" }` for request contexts, audit rows and logs.
2. **Authentication carries no organization.** Nothing in a session names an organization or a site (D-08). The tenant comes from the URL and is checked against membership by the tenancy module (M3-2). Sharing one host with tenant sites (ADR 0006) changes none of this.
3. **A new error kind, `Unauthenticated` (HTTP 401).** The error model (long-term §5.6) had `Forbidden` and `NotFound` but nothing for "no valid session". `requireUser()` throws it. `NotFound` still hides anything outside the caller's tenant.
4. **The 30-day cap is enforced twice.** The update hook (discovery 2) clamps `expires_at` when the session slides. `resolveAuth` also rejects, and deletes, any session whose `created_at` is 30 days old, so the cap does not depend on which path last wrote `expires_at`.
5. **Origin and CSRF checks are pinned on.** Better Auth turns both off by itself when `NODE_ENV` is `test`. The configuration sets `disableOriginCheck: false` and `disableCSRFCheck: false`, so they are on everywhere and the tests exercise them.
6. **Reset tokens and OAuth state are stored hashed** (`verification.storeIdentifier: "hashed"`, SHA-256). Reading `auth_verifications` yields no usable token. No schema change.
7. **Password reset:** the token lives 60 minutes, works once, and a successful reset deletes every session of the user (`revokeSessionsOnPasswordReset`).
8. **Endpoints V1 does not use are disabled:** `/change-email`, `/delete-user`, `/link-social`, `/unlink-account` answer 404.
9. **Configuration.**
   - `BETTER_AUTH_URL` is optional and defaults to `APP_ORIGIN`.
   - `BETTER_AUTH_SECRET` is required, except when the origin is `localhost` (or `*.localhost`) and the app is not on Vercel; a fixed development secret is used there, with a warning.
   - Google needs both variables or neither. Without them the Google routes answer 404.
   - `auth` is now a required env group: readiness reports it. A missing secret makes `/api/auth/*` answer 503, not crash at import.
10. **Logs.** Better Auth's own log lines go through Forge's logger (JSON, request id). Email addresses are removed from messages: Better Auth writes the address into its "sign-up attempt for existing email" line.

### One origin: the admin session and public site pages (ADR 0006)

The session cookie is host-only with `Path=/`, so a browser also sends it with `/s/{address}` requests. Three things keep the admin session away from public rendering:

- **The proxy removes `Cookie` and `Authorization` from every site request** before the renderer runs (`forwardedHeaders` in `platform/routing/hosts.ts`). Site pages cannot read the session, whatever their code does, and cannot vary by it, so the shared cache is safe.
- ESLint forbids importing the session helpers from `(sites)` code (`noSessionInSites`).
- Server Actions on site paths answer 404 (ADR 0002).

The cookie stays `HttpOnly`, `SameSite=Lax`, host-only, and `Secure` with the `__Secure-` prefix on https. A narrower cookie `Path` is not possible: the admin lives at `/`.

What remains is the consequence of one origin that ADR 0006 already records: script running on a `/s/…` page is same-origin with the admin. It cannot read the `HttpOnly` cookie, but it could call admin endpoints with it. V1 therefore must not let tenants put script on site pages (M5 sanitises content; embeds are sandboxed iframes). Moving sites to their own hosts post-V1 removes the issue.

### Account enumeration

| Flow | Behaviour |
|---|---|
| Sign-in | Wrong password and unknown email: the same status and body |
| Password reset request | Known and unknown email: the same response; no email is sent for an unknown address |
| Sign-up | **Reveals that an address is registered** (422) |

Sign-up reveals it because the plan lets users sign in before verifying (§12): Better Auth returns a generic sign-up response only when verification is required first. Changing that would change the plan, so it stays. M2-4's rate limit and Turnstile bound the abuse.

`authErrorToAppError()` gives the UI (M2-2) Forge's own messages. Unmapped errors return `null` and must be treated as unexpected: Better Auth's text is never shown.

### For M2-4: the rate limiter

Better Auth's limiter is on in production with its defaults: 3 requests per 10 s per client address for sign-in and sign-up, 3 per 60 s for reset and verification emails. It reads the address from `x-forwarded-for`, which Vercel sets. When the header is missing or lists several addresses, all clients share one bucket per path. Counts are in memory, per instance (discovery 8). M2-4 owns tuning it and the WAF rule.

### For M2-2: Cache Components

`getCurrentAuth()` reads request headers, so a page or layout that calls it must do so inside `<Suspense>` (discovery 9). Route handlers and Server Actions are unaffected. `/api/app/session` returns the signed-in user for the admin UI.

### Evidence

- `src/modules/auth/*.test.ts` (42 unit tests): the session mapping, the 30-day boundary, authenticated and anonymous resolution, the guards, the error mapping table, configuration, and log scrubbing.
- `tests/integration/auth.test.ts` (33 tests, real Postgres through PgBouncer): the 16 spike tests plus
  - fresh / idle-expired / older than 30 days / logged out / revoked sessions through `resolveAuth`;
  - password reset through `email.send` (single use, expiry, sessions revoked, unknown address, hashed storage, nothing in logs);
  - CSRF and open-redirect rejection; disabled endpoints;
  - Google optional and, when configured, PKCE + state;
  - a session reveals only its own user's organizations.
- `tests/unit/proxy.test.ts` and `platform/routing/hosts.test.ts`: credentials are stripped from site requests and kept for the admin and API.
- `tests/e2e/auth.spec.ts` (5 tests, production build, Mailpit): sign up → verify by email → authenticated route → log out → 401 → log in; password reset by email; foreign-origin rejection; site pages neither see nor set the session.

Mutation checks: removing the on-read 30-day check, the cookie stripping, or session revocation on reset each fails a test.
